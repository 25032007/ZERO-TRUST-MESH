# Zero-Trust Mesh

## What it is

A **zero-trust policy-enforcement proxy for service-to-service traffic**. Every request between microservices is authenticated with a signed identity, checked against a default-deny policy, scored for risk, and recorded in a tamper-evident audit log. Nothing is trusted because it is "inside the network".

## Quick start

```bash
npm ci
npm test
npm run demo
npm run dev
```
*(The dashboard runs at `http://localhost:4000`)*

## Architecture

The proxy intercepts traffic and routes it through an 8-stage security pipeline before hitting the downstream service:
1. **Rate Limit**: Service-level request quotas.
2. **Authenticate**: Ed25519 signature, expiration, algorithm pinning, and single-use jti replay checks.
3. **Quarantine**: Rejects requests if the calling service is currently quarantined.
4. **Authorise**: Evaluates default-deny, priority-based JSON policies (methods, paths, time windows, declared workflows).
5. **Payload Anomaly**: Statistical evaluation of body size and JSON depth against a rolling z-score.
6. **Lateral Movement**: Blocks and quarantines services that traverse 3+ distinct hops inside 1s within a single trace.
7. **Risk Score**: Accumulates points from soft signals and anomalies into a final explainable score.
8. **Verdict**: Decides `ALLOW`, `MONITOR`, `STEP_UP_AUTH` (TOTP required), or `BLOCK` (and quarantine).

## How the risk score is calculated

The total risk score is the sum of the following factors (defined in `src/config.ts`):

| Factor | Points |
|--------|--------|
| New Service Pair | 10 |
| Sensitive Endpoint | 10 |
| Off Hours | 5 |
| Burst Warn | 10 |
| Burst High | 20 |
| Rate Spike Elevated | 10 |
| Rate Spike High | 20 |
| Per Recent Auth Failure | 5 (max 25) |
| Lateral Movement | 50 |

Verdicts are assigned as follows: `< 30` (ALLOW), `30-59` (MONITOR), `60-79` (STEP_UP_AUTH), and `≥ 80` (BLOCK + Quarantine).

## Policy as Code

Policies are strictly validated JSON. Features include:
- **Priority**: Higher priority policies take precedence.
- **Default Deny**: Tie-breaks fail-safe to deny.
- **Dry-run**: Test policies safely. In global or per-policy dry-run, denials are flagged but the request is permitted.
- **Hot Reload**: Editing the policy file on disk updates the live engine atomically without a restart. Invalid edits are safely rejected.
- **Declared Workflows**: Specify exactly which service topologies (`svc-a -> svc-b -> svc-c`) are permitted, bypassing heuristic lateral movement blockers.

## Key Management

- **Public Key Only**: The proxy stores public keys only. Workloads mint and sign their own tokens.
- **JWKS Endpoint**: `GET /.well-known/jwks.json` serves active, valid public keys to external verifiers.
- **Rotation**: Configurable auto-rotation overlaps old and new keys for a grace period, ensuring zero downtime.
- **Revocation**: The admin API can instantly revoke a key without waiting for the grace period.

## Least-Privilege Recommender

The proxy tracks actual permission usage and surfaces suggestions via `GET /api/policies/recommendations`. It proposes narrowing wide paths, dropping unused policies, and surfacing denied edges for human review, reducing the risk of over-provisioned policies.

## Known Limitations

- **In-memory state**: Uses memory for JTI stores, rate limits, and audit logs. No Redis integration yet (though a `JtiStore` interface exists).
- **No mTLS**: Traffic between proxy and backends is plain HTTP on loopback.
- **Lateral-slow miss**: The `lateral-slow` attack class is intentionally missed because it spreads traversal over 8s, bypassing the 1s time window.
- **Synthetic evaluation**: The evaluation uses synthetic data generated by the same author who wrote the detector, meaning real-world performance is likely lower.
- **Ed25519 is not quantum-resistant**: Cryptographic identity relies on standard Ed25519.
